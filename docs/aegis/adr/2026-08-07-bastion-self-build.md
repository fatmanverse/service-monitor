# ADR：自建堡垒机而非集成开源方案

## 状态

已接受。此决策与「一体化平台」的产品定位强绑定，若定位变化需重新评估。

## 背景

平台需要提供堡垒机能力：主机登录、会话录像、命令审计、细粒度授权。成熟开源方案（Teleport、JumpServer）已实现这些功能并经过大量攻防检验。

自建的风险不容轻视。堡垒机是安全边界设备，一旦被攻破，攻击者获得的是全部纳管主机的最高权限。这个风险等级远高于平台的其他模块——监控失效只是少看几张图，堡垒机失守是全军覆没。

因此默认倾向应当是集成而非自建。本 ADR 记录为何在此项目中做出相反选择。

## 决策

自建堡垒机模块，通过已有的 Agent 通道实现 PTY 代理与会话录像。

决定性理由是**实体模型与授权必须唯一**。集成方案会引入第二份主机清单与第二套授权体系：

- Teleport 有自己的 node 注册机制与 RBAC 规则
- 平台有自己的 `assets` 表与 `role_bindings`

两者必须持续双向同步。同步是最脆弱的集成点：新增主机时同步延迟导致无法登录；撤销授权时同步失败导致越权访问窗口。后者是安全事故，而它的根因不在任何一方的代码里，在胶水层。

用户明确要求「一体化，而不是分散开来」。若堡垒机的授权真实来源在 Teleport 而非平台，那么「统一权限」这一核心承诺就不成立——平台只是一个把用户跳转出去的门户。

第二个理由是**联动能力**。平台的价值主张之一是在服务详情页看到「最近有谁登过这台机器、执行了什么、与哪次部署相关」。这要求会话记录与平台的资源、部署、审计在同一数据模型内可关联查询。集成方案下会话数据在外部系统，只能做到跳转查看，无法做关联分析与自动化响应（如「检测到生产环境高危命令，自动通知并冻结会话」）。

第三个理由是**Agent 通道已经存在**。自建堡垒机所需的「在远端主机上执行程序并双向传输字节流」能力，是 Agent 实时通道的直接应用，不需要新的接入机制。这显著降低了自建的增量成本——不必再为堡垒机单独设计一套主机接入与身份认证。

## 备选方案与否决理由

**集成 Teleport，同步资产与授权。** 安全性最有保障，实现成本最低。否决原因如上：双份实体模型与授权同步的脆弱性，与一体化定位冲突。

**集成 JumpServer。** 中文生态更完善，运维习惯更贴近国内团队。否决原因同上，且 JumpServer 的架构比 Teleport 更重，引入的运维负担更大。

**自建但仅做 SSH 转发，不做录像与审计。** 实现最轻。否决原因是失去了堡垒机的核心价值——没有审计的跳板机不如直接给用户 SSH 权限，反而增加了一跳故障点。

**混合模式：平台做授权，Teleport 做执行与录像。** 试图两者兼得。否决原因是授权与执行分离会产生时序问题——平台撤销授权的瞬间，Teleport 中已建立的会话是否立即终止？这需要额外的会话生命周期同步，复杂度不低于自建。

## 代价与缓解措施

自建的安全风险是真实的，必须以工程纪律对冲。以下措施为强制项，不是建议项：

**默认拒绝的授权模型。** 无显式 `role_bindings` 授权即拒绝登录，不存在任何默认允许路径。授权检查在会话建立时与会话期间周期性执行，撤销授权立即终止在途会话。

**会话录像不可篡改。** 录像分片写入对象存储后计算校验和并记录，平台自身不提供删除接口。任何对录像的修改都会导致校验和失配并在审计中暴露。

**危险命令识别与阻断。** 维护高危命令模式库（`rm -rf /`、磁盘操作、批量删除等），命中时按策略拦截或要求二次确认。此机制默认对生产环境资源启用。

**登录凭据由平台托管，用户不接触。** 用户通过平台身份认证，平台使用托管的密钥或短期证书登录目标主机。用户始终不持有目标主机凭据，因此撤销平台授权即完全断绝访问。

**独立的安全审查。** 堡垒机模块的代码变更必须经过专门的安全评审，评审范围至少覆盖：授权绕过路径、命令注入、录像完整性、会话隔离。此要求写入 `BASELINE-GOVERNANCE.md`。

**实施顺序靠后。** 会话代理排在阶段三，在资产模型、授权、审计、Agent 通道全部稳定之后。不允许为赶进度而跳过前置阶段——在不稳固的授权模型上构建会话代理是最危险的组合。阶段三启动前须按本 ADR 的「重新评估触发条件」复核自建决策是否仍然成立。

## 重新评估的触发条件

出现以下任一情况时应重新评估本决策：

- 安全审查发现难以在自建架构内修复的结构性缺陷
- 项目定位从「内部一体化平台」转向「对外销售产品」，合规要求（等保、审计认证）使自建成本急剧上升
- 纳管规模超出自建实现的性能边界，而开源方案已解决该规模问题
