# ADR：拓扑关系以观测数据为唯一来源

## 状态

已接受。

## 背景

平台需要提供服务与主机的拓扑图。拓扑图的技术难点不在渲染——前端图库（Cytoscape、D3）可以在数天内产出可用效果——而在**关系数据从何而来，以及如何保持它与现实一致**。

一张与现实不符的拓扑图比没有拓扑图更危险：运维人员会基于错误的依赖关系判断故障影响面，得出错误结论并采取错误行动。

## 决策

拓扑关系只接受可自动观测的来源，禁止将人工录入作为关系的唯一依据。

按可靠性与实现成本排序，分三个来源层次：

**第一层：部署关系（阶段三产出，成本最低）。** CI 部署记录天然包含「代码仓库 → 服务 → 主机」的映射。每次部署都会刷新这个关系，因此它不会腐烂。这一层能回答「这个服务跑在哪些机器上」「这个仓库影响哪些服务」。

**第二层：运行时连接（阶段四，需 Agent 采集）。** Agent 周期性采集本机的 TCP 连接（`ss -tnp` 或读取 `/proc/net/tcp` 并关联进程），上报「本机进程 → 远端地址:端口」。中心侧将远端地址反查到已纳管的资源，形成服务间的调用关系。这一层能回答「谁在调用我」「我依赖了谁」。

关键设计：每条关系记录 `last_observed_at`。超过阈值未再观测到的边标记为过期并从默认视图中移除。这是防止拓扑腐烂的核心机制——关系的存续依赖持续观测，而非一次录入。

**第三层：人工标注（补充，不可单独成立）。** 允许人工补充观测不到的关系（如异步消息队列的生产消费关系、外部第三方依赖）。但人工标注必须显式标记来源为 `manual`，在界面上与观测得来的关系视觉区分，并要求定期复核。人工标注不参与「故障影响面自动分析」这类高风险推断。

## 备选方案与否决理由

**以人工维护的服务清单与依赖声明为主。** 实现最简单，无需采集。否决原因是必然腐烂——服务上下线、依赖变更不会有人同步更新拓扑，三个月后图与现实完全脱节。这是拓扑图项目最常见的失败模式。

**从配置文件解析依赖（如解析服务的 application.yml）。** 能获得声明式依赖。否决原因是配置格式千差万别，解析器需要按技术栈逐个适配，且声明的依赖与实际调用可能不符（配了但没用、用了但没配）。可作为第三层的辅助输入，不作为主来源。

**eBPF 采集网络流量。** 数据最精确，能捕获完整调用链与流量大小。否决原因是内核版本要求高（部分 CentOS 7 环境不满足）、Agent 需要更高权限、实现与排障复杂度显著上升。列为第二层的未来增强项，不作为初始实现。

**接入服务网格（Istio 等）的遥测数据。** 数据质量最高。否决原因是要求目标服务已在网格内，而平台需要纳管的大量传统服务不在网格中。可作为已上网格服务的额外数据源。

**直接使用 Prometheus 的服务发现数据。** 复用现有能力。否决原因是 Prometheus 的 target 列表只说明「谁被采集」，不包含服务间调用关系，无法构成拓扑。

## 后果

**正面。** 拓扑图具备自我更新能力，不需要人工维护即可保持与现实一致。关系带观测时间戳，可以回答「这个依赖是什么时候消失的」。第一层几乎零成本，在阶段三完成后即可提供有价值的部署视图。

**负面。** 第二层需要 Agent 具备采集能力并上报，增加 Agent 的职责与数据量。TCP 连接采集是抽样的（采集周期之间的短连接会被漏掉），因此低频调用关系可能观测不到——这是抽样固有的局限，需在界面上说明拓扑的完备性边界，避免用户误以为图上没有的边就一定不存在。

**风险。** 连接数据涉及内部网络结构，属于敏感信息。访问拓扑视图需要相应授权，且采集数据中不得包含连接内容（只记录地址、端口、进程，不记录传输的数据）。

## 实施顺序

拓扑图排在阶段四（最后），原因是它的数据依赖前置阶段的产出：第一层依赖阶段三的部署记录，第二层依赖阶段一稳定的 Agent 通道。提前实现只能得到人工维护的版本，而这已被明确否决。
