# ADR：Agent 采用双通道模型区分可靠投递与实时交互

## 状态

已接受。

## 背景

Agent 与平台之间存在两类性质截然不同的交互：

**需要可靠投递的**：配置下发、探活结果上报、异步命令（重启服务、执行部署）。这类交互不能因为网络抖动而丢失——一次部署命令投递失败意味着发布静默失效。允许秒级甚至分钟级延迟。

**需要实时性的**：交互式终端、实时日志跟随。这类交互对延迟敏感（输入回显超过 200ms 即明显卡顿），但断线即结束，不需要持久化——用户会重新打开终端。

若用同一套机制承载两类交互，必然在某一侧做出错误取舍：全部走持久化队列则终端不可用，全部走内存流则命令会丢失。

同时，Agent 部署在客户内网，平台无法主动连接，必须由 Agent 主动外连。

## 决策

Agent 通过 gRPC 双向流主动连接 `agent-gateway`，在同一条 TCP 连接上区分两类通道。

**控制通道（durable）**：以数据库 `tasks` 表为权威队列。Agent 通过流接收「有新任务」的轻量通知后，主动拉取任务详情并执行，完成后上报结果。断线期间任务留在队列，重连后继续处理。通知丢失不影响正确性——Agent 也会周期性主动拉取作为兜底。

**实时通道（ephemeral）**：直接在双向流上传输消息，不落库。用于 PTY 字节流与日志跟随。连接断开即会话终止。

连接归属写入 Redis：`agent:{uuid} → gateway:{node_id}`，带 TTL 并周期续期。当任意 api-server 副本需要向特定 Agent 推送实时消息时，查 Redis 得到归属网关，通过 Redis Pub/Sub 投递到该网关副本，由它写入对应的流。

## 备选方案与否决理由

**统一走数据库队列（含终端输入）。** 实现最简单，只有一套机制。否决原因是终端每次按键都要经过一次数据库写入与轮询读取，延迟不可接受，且会把 `tasks` 表写入量放大数个数量级。

**统一走内存流（含部署命令）。** 延迟最优。否决原因是网络抖动会导致命令丢失，而平台无法区分「命令已执行」与「命令未送达」。对于部署这类有副作用的操作，这种不确定性不可接受。

**Agent 暴露 HTTP 端口由平台主动调用。** 模型最直观。否决原因是要求 Agent 所在网络对平台开放入站端口，在多层 NAT 与严格防火墙的内网环境中不可行，且扩大了 Agent 的攻击面。

**为两类交互建立两条独立 TCP 连接。** 隔离更彻底。否决原因是连接数翻倍，且两条连接的存活状态可能不一致，导致「控制通道在线但实时通道断开」这类需要额外处理的中间态。

## 代价

**实时通道依赖 Redis 可用性。** Redis 故障时无法定位 Agent 归属网关，交互式终端不可用。这是有意接受的取舍：核心运维能力（配置下发、探活、部署）走控制通道不依赖 Redis，因此 Redis 故障降级为「不能开终端」而非「平台不可用」。此依赖边界必须在运维文档中写明，避免故障时误判影响面。

**网关是有状态组件。** 持有 Agent 长连接，不能像 api-server 那样随意重启。滚动发布会导致 Agent 集中重连，需要 Agent 侧实现带抖动的指数退避，避免重连风暴。

**连接归属信息可能短暂失准。** 网关崩溃后 Redis 中的映射在 TTL 到期前仍然存在，此期间向该 Agent 发送实时消息会失败。通过较短 TTL（30 秒）与发送失败后重查缓解。

**Agent 侧需要实现两套消息处理路径。** 增加 Agent 复杂度。缓解方式是在协议层用 message 的 oneof 明确区分，两类消息的处理逻辑完全隔离。

## 影响

- protobuf 协议需明确区分控制消息与实时消息，不共用消息类型。
- Agent 必须实现带抖动的重连退避。
- 运维文档必须写明 Redis 故障时的降级边界。
- 网关的发布策略与 api-server 不同，需要考虑连接优雅转移或接受重连。
