# Aegis 文档体系

本目录是平台的架构基线。目标是让「为什么这样设计」与「设计是什么」一样可追溯。

## 目录职责

| 目录 | 内容 | 何时写 |
| --- | --- | --- |
| `specs/` | 设计规格：目标、不变量、数据模型、模块设计 | 功能开发前，需用户确认 |
| `adr/` | 架构决策记录：面临的选择、决策、否决理由、代价 | 出现有长期影响且存在多个可行方案的决策点 |
| `plans/` | 实施计划：工作项分解、依赖顺序、验证方式 | 规格确认后，开工前 |
| `work/` | 工作记录：意图、检查点、证据、反思 | 实施过程中持续更新 |

## 写作要求

**规格必须包含不变量与非目标。** 只写「要做什么」的规格无法防止范围蔓延，也无法在评审时发现设计冲突。

**ADR 必须写否决理由与代价。** 只记录最终选择的 ADR 价值有限——后来者会重新提出已被否决的方案。必须写清备选方案为何不适用，以及当前选择付出了什么代价。

**实施计划的每个工作项必须有验证方式。** 「完成」不是主观判断。没有验证方式的工作项无法确认是否真的完成。

**文档中的技术断言必须可核查。** 引用代码时给出文件路径；引用容量数字时说明测算依据或压测方式。不写无法验证的论断。

## 文件命名

`YYYY-MM-DD-短横线分隔的主题.md`。日期为创建日期，不随修订变更。

`work/` 下按功能建子目录，内部文件使用数字前缀排序：`10-intent.md`、`20-checkpoint.md`、`90-evidence.md`、`99-reflection.md`。

## 变更规则

规格与 ADR 是基线，修改需要说明原因。发现设计缺陷时，先修订文档再改代码，避免代码与文档分叉。

ADR 一旦被后续决策取代，不删除原文，在状态中标记「已被 XXX 取代」并保留原始论证。
